# プラグイン・モデル・DSHの更新

「更新」が何を変える操作なのかを、画面と実装で分けます。設定の再読み込み、モデル候補の再取得、パッケージの差し替えは別の処理です。

## 更新するものを分ける

| 対象 | 操作例 | 変わるもの |
| --- | --- | --- |
| 画面の状態 | 再読み込み | Hostに保存された設定・接続状態の再取得 |
| 認証状態 | ログイン・再接続 | tokenや接続状態。SDKの対応モデルは増えない |
| モデルカタログ | モデル一覧を再取得 | 実装されている場合に、提供元から候補を取得 |
| Pi SDK | プラグインの依存更新と再配布 | SDKのprovider、model、認証・stream実装 |
| プラグイン | プラグインを更新 | Host・Clientコード、翻訳、同梱データ |
| DSH本体 | DSHを更新 | API、Loader、UI部品、起動環境 |
| Remora Hub・CLI | それぞれの配布物を更新 | 別プロセスのコードとプロトコル |
| 保存データ | migration | 既存の設定や履歴の形式 |

例えば日本語化プラグインを更新しても、DSH本体の新しい画面に対応する翻訳キーが追加されていなければ、その部分は翻訳されません。逆にDSHだけを更新すると、プラグインが参照していた内部APIが変わる場合があります。

## Piのモデル名はどう追従するか

確認したPiログイン`0.5.1`は、固定されたPi SDKのモデル情報を使います。SDKを更新してプラグインを再ビルド・配布すると、その版の対応内容に追従します。プラグインの更新ボタンが公開Releaseを導入することと、開発者がPi SDKを更新することは別です。

確認版は`@earendil-works/pi-ai`の`1.1.0`を使います。開発用の`npm run update:pi`はnpmのlatest版へ依存を固定し、SDKが変わった場合にpluginのパッチ版も上げる処理です。版を指定する引数もあります。更新差分を確認し、認証、モデル能力、stream、履歴、UIの関連テストを通してから再配布します。これは開発者の更新手順で、利用者の実行中DSHが自動でSDKを入れ替える処理ではありません。

新しいモデルを自動発見するカタログは[Issue #6](https://github.com/Aero123421/dsh-pi-login/issues/6)、他のプラグインのプロバイダーをまとめて表示する機能は[Issue #7](https://github.com/Aero123421/dsh-pi-login/issues/7)として、2026-10-13の確認時点で未完了です。ログインし直すだけで最新版SDKや新しい認証処理が入るとは案内しません。

APIが返すモデルIDだけでは、reasoning、画像、tool call、context長、OAuthの対象、Fastの可否は確定できません。動的カタログを作る場合は、次を設計します。

- 候補の取得元と、接続・認証を所有するプラグイン。
- 最後に正常取得した候補と、取得時刻。
- 未知の能力を「対応」と表示しないための検証。
- ユーザーのモデルON/OFFを、一覧更新後も保持する安定したID。
- 候補が消えたときの保存履歴・現在選択の扱い。
- 取得失敗時に、保存済み候補を使うか、利用を止めるかの明示。

SDKが実装していない認証フローやstream APIまで、一覧取得で自動対応することはできません。

動的catalogを実装している外部pluginの例として、[Subscriptionsの取得loop・cache・account管理](ecosystem/providers-and-memory.md)を調べています。Piへ取り込む場合も、providerの所有者とSDKの能力を確認します。

## GitHub指定の更新

`github:OWNER/REPO#v0.1.0`は、指定した版を導入するための指定です。GitHubに`v0.1.1`を作っても、導入済みprofileが自動でその版に切り替わるわけではありません。

更新時は新しいタグを指定して同じパッケージを差し替えます。CLIの操作例です。`OWNER/REPO`とタグは、更新対象の公開済みの値に置き換えます。

```sh
dsh plugin --profile web add -w github:OWNER/REPO#v0.1.1
```

同じ名前のパッケージを更新できることと、管理画面の新規追加フォームがその指定を受け付けることは別です。確認版の`inspect()`は、同名パッケージが既にある場合に`already-installed`を返す経路があります。更新用UIから新規導入用の検査をそのまま流用すると、この違いにぶつかります。

ブランチ指定やタグなしの指定は内容が変わり得ます。同じ`package.json.version`で内容だけ変わると、バージョン比較による更新検知はできません。配布する変更には版を付け、公開済みタグを別内容へ移動させない運用を推奨します。

## 更新時に保持する状態

| 状態 | 扱い |
| --- | --- |
| bundleのON/OFF | 更新前の値を保持。installerの既定値で勝手にONにしない |
| providerのON/OFF | 資格情報・選択モデルを削除せず保持 |
| モデル・追加ツールの選択 | 安定したIDで保持。利用可否はHostで再検査 |
| 資格情報 | コード更新と削除を分ける。移行は保存先の優先順位まで確認 |
| Session履歴 | 過去のモデル・ツール呼び出しを読み直せる形式を維持 |
| 設定形式 | 必要なmigrationを行い、失敗時に旧データを壊さない |

DSHの確認版では、既に導入されたパッケージを差し替えると`restart-required`になります。「新しいファイルが入った版」と「現在動いている版」を分けて表示します。

Web版はサーバーの再起動後にブラウザーを再読み込みします。PWAで初めてClient entryを追加した更新では、ブラウザー再読み込みだけでは新しい設定欄が出ませんでした。[原因と確認手順](update-and-restart.md)を参照してください。再起動を実行する機能は7つの更新ボタンに共通して搭載したものではありません。

## DSHの互換性を維持する

対応範囲は、`peerDependencies`だけでなく実際に試したDSH版も記録します。内部APIを参照している箇所を一覧にすると、上流更新時に調べる場所を絞れます。

上流更新では、公開entry、remote RPCの型、設定サービス、locale登録、ツール出力・履歴、UI部品のDOMやCSSを確認します。変更された境界のテストから実行し、関係のない全テストを毎回追加する必要はありません。

互換性エラーを消すために、版検査を黙って回避したり、不明な値を二重castで既存型に見せたりしません。DSH本体、プラグイン、Hub、CLIの組合せで互換性が必要な場合は、組合せを記録します。

## 更新に失敗したとき

旧版へ戻す手順と、保存データを戻せる範囲を区別します。旧コードを再導入できても、新形式の保存データを旧コードが読めるとは限りません。

資格情報や設定を消して入れ直す方法を、通常の更新失敗対応にはしません。まず操作結果、profileの保存状態、導入版、実行版を照合します。更新ボタンの結果判定は[次の章](update-button.md)にあります。
