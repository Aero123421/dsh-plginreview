# 詰まりどころの分析

この章は公開履歴からの工程分析です。非公開の会話や担当者の稼働を推定した評価ではありません。[自作の事例](own-cases.md)と[外部の事例](ecosystem-cases.md)に根拠があります。

## 1. 症状と原因仮説が一緒に渡される

PiではMuseの能力補正を撤回し、TUI #60ではpnpm更新・依存追加という初期案から、依存解決の起点へ調査が進みました。market #788では詳細なログの因果説明が訂正されています。

仮説を確定事項として実装へ渡すと、それに合うコードとtestを作れます。しかし、そのtestは利用者の失敗経路を確認していない可能性があります。CI成功が前提を補強してしまい、前提の訂正時には実装・期待値・文書をまとめて戻すことになります。

| 見分ける質問 | 次に置く確認 |
| --- | --- |
| 利用者が観察した値は何か。原因はまだ説明にすぎないか | 観察と仮説を別行にする |
| この仮説が違えば、何が起こるはずか | exact model、scope、resolved path、write eventなど該当境界を観測する |
| 旧実装でもtestが成功しないか | 問題の条件を戻した限定差分で失敗を確認する |

明確な再現のあるPi #1/#2では、この受け渡しは機能していました。すべてのIssueへ調査項目を増やす必要はありません。

## 2. 利用者の操作とAPIの仕様を同時に決める

Pi Fastでは、能力補正、APIのpriority指定、選択UIが同じPRで動いていました。接続できることと、どのモデル候補を選ぶかは別の判断です。

APIの実体が曖昧なままUIを作ると、表示名に能力を結び付けたり、別の認証routeへ同じ設定を適用したりしやすくなります。逆に、UIが未確定でもSDKの能力情報や公開entryの調査は進められます。

先に、利用者が選ぶ操作を一文で固定します。Fastなら「設定で通常版とFast版を別々にON/OFFし、チャットでは候補として選ぶ」です。その後、wire model、選択ID、tier、effortを結びます。動的カタログや他pluginの統合は、現在の修正の受け入れに必要な部分だけ扱います。

## 3. 状態の所有者を越えた修正が必要になる

Remoraの監査readとwriter、marketのprofileとDesktop generation、TUIのlauncherとmodule、modlensのglobalとagent scopeが該当します。担当が書き換えた状態を、利用者経路が読んでいるとは限りません。

詰まりは「別repoだから難しい」だけでは説明できません。同じrepo・process内でも、write完了、RPC応答、model-visible schemaの意味が違えば起こります。

次の3点を一つの経路で確認します。

1. 利用者の操作が最後に読む状態はどれか。
2. その状態を所有し、変更できる側はどこか。
3. その側が返す完了は、保存・反映・次回起動のどこまでか。

変更できない側へ万能な更新処理を追加するより、market #497のように通知へ留める方が正しい場合があります。根治、緩和、診断改善は、到達する範囲で区別します。

## 4. 非同期の成功を順序保証へ広げる

RemoraはPR CIが成功し、merge後に監査readが失敗しました。検索pluginは同じSHAのnative testに成功と失敗が並び、その後fixtureの再接続競合を直しています。

成功した一回の順序から、すべての順序が安全とは言えません。「flake」と呼んで再実行だけで進めると、製品の不足とtestの不足を分ける機会を失います。

barrierで、古い応答、write、cancel、disconnect、disposeを必要な位置で止めます。正常順序だけでなく、遅延成功と遅延失敗、取消後の次ターン、解除後のcallbackを確認します。待ち時間を伸ばす場合は、待つ対象と期限の根拠を示します。

## 5. 同じ「CI failure」で環境・test・製品をまとめる

Glass UIのpnpm不在、依存更新のpeer不一致、Remoraの保存待ち、検索fixtureの競合は、違う層の失敗です。失敗step名が同じでも原因は変わります。

| 失敗した層 | 先に確認すること | 修正を広げない範囲 |
| --- | --- | --- |
| runner準備・依存解決 | 必要tool、lockfile、peer条件 | 起動していないruntimeの不具合と断定しない |
| testの起動・終了・操作 | readiness、対話notice、reconnect、process exit | testだけの変更をAPI機能の修正としない |
| 製品の契約 | read/write順序、権限、scope、登録結果 | testの再試行で契約不足を隠さない |
| 配布・導入 | file集合、entry、取得元、実行版 | build成功を公開経路全体の成功にしない |

分類は調査の結果として行います。「CIだから環境だ」「ローカル成功だからtestが悪い」と先に決めません。

## 6. レビュー済みの意味が曖昧になる

代表PRにはbotのquota到達やskipがありました。COMMENTEDという状態だけを読むと、レビューが実行されたように見えます。一方、GitHub approvalがないことはローカル・agentレビューの不在を意味しません。

必要なのは、誰が何を対象に見たかです。`対象SHA / 検査した経路 / 実行した確認 / 残る条件`を短く残します。前提を撤回したり配布構成を変えたりした後は、その追加差分と影響する境界を確認します。

レビュー人数を増やすだけでは、同じ前提と同じfixtureを共有する見落としを減らせません。担当外の状態所有者、実agent scope、公開物、親DSH画面のうち、変更が通る別の観測点を選びます。

## 7. 検証の成功から適用範囲が落ちる

Remoraの実DSH E2Eは、後から追加したタブの幅assertionを持っていませんでした。Piのkeyless SDK試験はFastの契約別資格を確認せず、tarballの起動はGitHub sourceの起動を確認しません。

この境界で「テスト済み」だけ渡すと、次の担当が自分の必要な確認も済んだと読めます。結果には対象物と観測を付けます。

PWAの追加事例では、導入版`0.2.0`とRunning表示が確認できても、新しい設定欄はHost再起動まで出ませんでした。新規導入の成功を旧版起動中の更新へ広げないこと、ブラウザー再読み込みとサーバー再起動を分けることが必要です。[再現条件](../update-and-restart.md)を参照してください。

```text
実DSH Web profileへ公開tgzを導入し、Host/Client起動を確認。
日本語の全tab選択と背景の幅を確認。
実OAuthと別OSのkeychainは今回の対象外。
```

画面の場合はscreenshotだけでなく、選択された項目、buttonと背景の座標、実内容欄の幅を使います。APIの場合はHTTP成功に加え、要求した能力の受理・適用を区別します。

## 8. 配布の前提が別担当へ届かない

Glass UIはGitHub導入用distの追跡を加え、releaseの`dist/*`が新たなfileを拾いました。Pi・日本語化では未ビルドGitHub source、PWAではworkspace rootの制約が残っていました。

build担当が作る物、installerが取る物、release担当が公開する物を列挙します。`dist/`の存在やpackage rootが変わったら、後続workflowとREADMEの取得指定まで追います。

共通手順は複数repoへ横展開できますが、コマンドのコピーだけでは足りません。単一bundle、workspace内bundle、GitHub source、tarballで導入対象が違います。各READMEの実コマンドを隔離profileで確認するところまでを再利用します。

## 9. merge・公開・実行・解決を一つの状態にする

PiのIssueは公開前にclose、market #788は公開後にclose、TUI #60は最初の配布版を今回確定できませんでした。検索ではmain CI終了前にReleaseが公開されました。

一つの「完了」にまとめると、配布や実環境確認が後続作業として見えなくなります。必要な関連checkが並行中なら、公開側に同等の最終確認があるかを確かめます。関係のない全jobを待つ手順を一律に加えるものではありません。

Issueのclose運用は維持しても、修正SHA、含む配布版、導入指定、対象操作の結果を記録できます。実APIを確認していない場合はその条件を残し、機能全体を対応済みにしません。

## 10. 外部の不確実性を実装量で解こうとする

Pi Contributor Max、FxTwitter keyword、動的カタログ、他provider統合には、実APIの証拠や上流の識別契約が必要です。補正、独自API、UIを増やしても、上流が要求を受理することの証拠にはなりません。

| 現在の条件 | 次にすること |
| --- | --- |
| 再現情報が足りない | 必要な版・取得元・操作順のうち、一つの不明点を確認する |
| 原因候補が複数 | 仮説を分ける最小の観測を行う |
| 実APIが未確認 | exact route・要求・結果を記録できるsmokeを決める |
| 上流が状態を所有する | このrepoでできる緩和と、上流へ必要な契約を分ける |
| 実装済み・公開未確認 | 公開物の版・取得・対象操作を確認する |
| 将来の機能 | 現修正の完了条件から分け、設計判断を残す |

待機の理由は証拠があるものだけ書きます。「openだから詰まり」「実API未確認だから鍵待ち」という推定はしません。

## どこから改善するか

この標本では原因別頻度や工程の稼働率を出せません。実例に近い変更から、確認を置く位置を選びます。

- 公開entry・build・取得指定の変更では、配布物を使う導入確認を優先する。
- 非同期・保存・取消の変更では、完了の意味と失敗する順序を優先する。
- UIの変更では、親DSH・言語・内容幅・選択状態の観測を優先する。
- providerの変更では、実体の識別と、fixture・SDK・実APIの能力の区別を優先する。

全testの追加、全OSの実行、大きい承認手続きを先に増やす改善は、この調査からは導いていません。変更が通る境界を直接確認し、その効果を次の仕事で追います。
