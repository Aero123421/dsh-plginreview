# 解決までの進め方

Issue、PR、会話のどこから始めても、利用者の失敗経路を追います。以下は[事例分析](README.md)を次の仕事に使うための手順です。すべての欄・試験を全変更に要求するものではありません。

## 1. 最初に固定する

最初の記録は次の4行で足ります。

```text
対象: plugin版・DSH版・取得元と、症状に関係する環境
症状: 操作の順序、期待した結果、実際の結果
根拠: 再現、file位置、短い診断。原因仮説は別記
受け入れ: 修正後に利用者が行える操作・残る条件
```

modelならexact provider/model/route、UIならlocale/theme/実内容幅、依存ならresolved pathを足します。無関係な環境情報まで集めません。秘密の値を診断やsnapshotに残さず、接続状態・認証方式など必要な情報を使います。

## 2. 原因を絞り、変更する側を決める

仮説を否定できる観測を先に選びます。能力欠落ならSDKカタログと実model ID、tool不在なら実agent scope、設定が戻るなら古いreadの完了、更新が戻るなら次回起動の設定です。

plugin、Host、Client、SDK、registryのどこが状態を所有するかを確認します。このrepoで根治できない場合は、正しくできる緩和の範囲を決めます。診断改善だけの場合は、元の操作まで直ったと記録しません。

## 3. 分担は失敗経路の境界で行う

複数agentを使う場合、ファイル数を均等に割る前に、共有する契約を決めます。

| 担当例 | 単独で調べる・変更する範囲 | 統合時に揃えること |
| --- | --- | --- |
| provider・adapter | 認証、model ID、能力、request/stream | 設定とmodel pickerに同じ候補が出るか |
| 保存・Host | lock、権限、read/write、取消対象 | RPC応答時の保存保証、Clientの表示 |
| Client | load/save世代、登録解除、親DSH画面 | 古い成功・失敗、再接続、Hostの結果 |
| build・配布 | exports、patch、生成物、pack、公開asset | 利用者の取得指定から同じ版が起動するか |

共有設定や公開契約を変える担当を明示し、別担当が同じfileを同時に書き換えないようにします。独立した読解・再現は並行できます。最後は統合する担当が、各報告を同じ最終差分へ照合します。

引き継ぎは短く、次の内容を残します。

```text
対象SHA / 触った境界 / 確認した失敗経路
共有状態の所有者 / 完了の意味 / 他担当の前提が変わる点
実行した確認と結果 / 未確認 / 次に必要な操作
```

Remoraなら「監査RPCはwriterのflushを待つ」。Glass UIなら「distがGit追跡になるため、release uploadの入力集合が変わる」です。担当ファイルの一覧や「テスト済み」だけでは、この情報を渡せません。

## 4. 修正と回帰確認を対応させる

指摘ごとに、失敗条件、修正、確認を結びます。可能なら旧挙動を戻した限定差分で失敗を確認します。非同期はbarrier、UIは実hostの観測、公開entryは配布物で試します。

仕様が変わったら、期待値・docs・PR本文も最終仕様へ揃えます。撤回した案を完成版の説明に残しません。モデルへの指示を変えないUIの仕事で、応答言語やsystem promptをついでに変更しません。

## 5. レビューは最終差分へ結ぶ

レビュー対象SHAと、調べた経路を記録します。追加差分があれば、影響する境界を確認して結論を更新します。成功済みの無関係な確認を、commit・pushのためだけに繰り返しません。

botが実行不能なら、その状態をレビュー成功へ置き換えません。別agentやローカルの確認を行った場合は、その対象と内容を残します。GitHub approvalの数だけでレビューの有無を決めません。

CIが失敗したら、次を読む順序にします。

1. どのSHA・event・attemptか。
2. 最初に失敗したstepは何か。後続は実行されたか。
3. 環境、test、製品、配布のどの層か。
4. 修正した条件は何か。旧条件で失敗するか。
5. 修正後の関連runが成功したか。

同じSHAの別runが成功しても、順序競合を解消した証拠にはしません。[テストとCI](../testing.md)の隔離・終了・回帰確認を使います。

## 6. 公開する物と、利用者が取る物を確認する

最終SHA、package版、使うrefまたは配布物、導入指定を対応させます。配布fileにchecksumが提供される場合は照合します。新規導入だけでなく、変更に関係する旧版更新・OFF状態・保存設定・解除を選んで確認します。

公開前は予定する取得物を確認し、公開後は実際のURL・tagから取って、対象操作と実行版を確認します。source build、未公開artifact、公開assetを同じ証拠として扱いません。必要な関連checkが並行中なら、公開判断に使う確認を明示してから進めます。

単一bundleとworkspace内bundleの導入先は違います。[インストール](../installation.md)、[公開手順](../release.md)、[更新の完了](../update-button.md)を参照してください。

## 7. closeと配布後の残件を結ぶ

Issueをmerge時にcloseする運用でも、次の記録を残せます。

```text
修正: PR / SHA
配布: その修正を含む版・取得指定
確認: 配布物で試した対象操作と結果
残る条件: 実API・別OSなど今回の結論に関係する未確認
次: 残る確認を進める操作・必要な条件
```

公開予定なら予定と書き、配布版が未確認なら空欄を成功へ埋めません。利用者の追認が得られたら、その環境と結果を結びます。再発時は元の再現と同じかを確かめ、UI方針の変更や別機能を再発件数に混ぜません。

記録は[テンプレート](../../templates/issue-resolution.md)を使えます。書く場所はIssue、PR、review reportの一つで十分です。他の場所からリンクし、同じ結果を複製して食い違わせません。

## 改善の効果を確かめる

次の数件では、従来と比べて確認の位置が変わったかを見ます。新しい監視・自動化を常設する必要はありません。

| 残す観測 | 判断できること |
| --- | --- |
| 不具合を発見した工程 | 利用者への公開前に見つかったか |
| 追加修正の理由 | 前提訂正、別条件、test、配布、仕様変更のどれか |
| 修正前に失敗する確認 | 確認が元の症状を捕まえたか |
| 対象SHAと実行版 | 古い確認や別成果物を使っていないか |
| 公開物の導入・対象操作 | 修正が取得・実行経路を通ったか |
| 実APIなどの残件と次の操作 | 未確認がcloseで消えていないか |

待ち時間を測る場合は、理由・待ち始め・解除条件が記録された区間だけを使います。Issue作成からmergeまでを全て待ち時間や作業時間にしません。テスト件数、agent人数、botコメント数、CI run数を品質目標にせず、同じ失敗条件の再発と公開後の追加修正を追います。
