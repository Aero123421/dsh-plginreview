# レビューの進め方

レビューでは、公開物をDSHに入れたときの動作を確認します。型検査が通ること、見た目が整っていること、開発サーバーで動くことは、それぞれ確認の一部です。

## 1. 対象を固定する

対象コミット、DSHの版、Nodeとパッケージマネージャーの版を記録します。レビュー中に対象ブランチが更新されたら、追加差分を確認してから結論を更新します。

最初に次のファイルを読みます。

| 場所 | 確認すること |
| --- | --- |
| `package.json` | 名前、版、ESM、exports、files、依存、DSH bundle/client宣言 |
| `cordis.patch.yml` | 実際に登録するプラグイン、ID、既存設定への影響 |
| Host entry | サービス依存、RPC、設定保存、資格情報、外部通信 |
| Client entry | 接続世代、設定読み込み、保存、登録解除、表示条件 |
| build・packスクリプト | 公開entryと生成物が一致するか |
| CI・release workflow | 何を検証し、何をアップロードするか |
| README | ユーザーが実行する導入手順と、実装の対応範囲 |

リポジトリのルートが開発用workspaceでも、インストール対象はその中の別パッケージという場合があります。Remoraではこの区別が必要です。

## 2. 実際のLoader構成で起動する

まず公開entryを読み込めるか、その後にCordisの登録を確認します。

- `exports`の先がGitHub取得物と`.tgz`の両方に存在する。
- bundleのpatchが配布物に入り、記載した`name`が解決できる。
- 必須サービスが登録される順序と依存宣言が合う。
- HostとClientを、それぞれの環境向けにビルドしている。
- プラグインIDと設定namespaceが一致する。
- HMRで解除して再登録しても、ツール・イベント・CSSが二重にならない。

DSH本体のソースを相対importして開発時だけ動く構成は避けます。公開SDK、package名、DSHの既存拡張点を使い、必要な内部API依存は[互換性の確認対象](updates.md)として記録します。

## 3. 状態の変化を順番ごとに調べる

画面を一度開いて確認するだけでは、非同期の不具合を見落とします。次の順序を試します。

| 操作の順序 | 調べる問題 |
| --- | --- |
| 読み込み開始 → 設定変更 → 古い読み込み完了 | 新しい選択が古い値で戻る |
| 保存A → 保存B → Aの失敗 | BがAの巻き戻しで失われる |
| A → B → Aと編集 → 最初のAが完了 | 値が同じという理由で別の操作を取り違える |
| 接続Aで取得 → 接続Bへ切り替え → Aの失敗 | 現在の接続に古いエラーが表示される |
| 処理開始 → 無効化・解除 → 処理完了 | 解除後に再登録・書き込みが起きる |
| 遠隔操作開始 → 権限縮小 → 結果取得 | 開始時の権限だけで結果を返す |
| 接続切断 → Host側の処理完了 → 再接続 | 完了した仕事が永久に実行中になる |

Abortだけに依存せず、古い成功・失敗の両方を採用しない仕組みを確認します。世代ID、リクエストID、編集オブジェクトの識別、直列化のうち、所有する状態に合う方法を選びます。

## 4. Hostで境界を確認する

Clientがボタンを隠しても、RPCを直接呼べる場合があります。権限、プロバイダー有効状態、モデル選択、入力サイズ、URL、保存データの検査はHost側にも必要です。

外部APIのレスポンス、設定JSON、workerやprocessからの値は、TypeScriptの型だけでは検証できません。未知の値、欠けたフィールド、誤った型、極端に大きいレスポンスをテストします。

秘密情報の値をsnapshotや診断に含めず、「保存済み」「未接続」など必要な状態だけを返します。権限とデータ整合性は[権限・保存・外部通信](security-and-storage.md)で詳しく扱います。

## 5. UIを実物で確認する

独立したプレビューに加え、DSHの設定モーダルに入れて確認します。左ナビゲーション、スクロール、組み込み部品の幅計算が影響するためです。

少なくとも、日本語、明暗テーマ、狭い設定パネル、キーボード、読み込み、失敗、読み取り専用、解除を確認します。画像だけでなく、実際に選ばれた項目やボタンの座標も確認します。[UIの確認方法](ui.md)を参照してください。

## 6. 不具合を報告する

報告には、次の5点を入れます。

1. 具体的な発生条件。
2. 利用者に起きる影響。
3. 原因を示すコード位置や再現結果。
4. 修正すべき境界・処理。
5. 修正前で失敗し、修正後で成功する確認方法。

「競合しそう」「安全ではないかもしれない」だけでは、確認済みの不具合にしません。根拠のある設計上の懸念と、再現した不具合を分けます。

| 優先度の目安 | 例 |
| --- | --- |
| P0 | 直ちに止める必要がある、広範な侵害・データ損失 |
| P1 | 権限を越える操作、秘密情報漏えい、通常操作でのデータ損失、起動不能 |
| P2 | 設定が戻る、更新失敗を成功表示する、主要操作のUI不具合 |
| P3 | 操作を妨げない表示・文言・保守上の問題 |

優先度は発生条件と影響から決めます。表中の例だけで機械的に決めません。

## レビュー後の確認

修正した範囲のテストを実行し、実行コマンドと結果を記録します。モック成功、実DSHでの成功、実APIでの成功は区別します。公開entryや配布形式を変えた場合は、生成した配布物を再度インストールします。

報告は[テンプレート](../templates/review-report.md)に記録できます。具体例は[よくあった問題](common-problems.md)、確認の組み方は[テストとCI](testing.md)にあります。

公式・外部の実装を比較する際は、[調査一覧](ecosystem/README.md)と[配布物・版条件の結果](ecosystem/package-checks.md)も使えます。紹介文、ソース読解、単独検証、実DSHでの結果を区別して報告します。
